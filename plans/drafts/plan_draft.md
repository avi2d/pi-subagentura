## RALPLAN-DR Summary

### Mode

DELIBERATE — public API change (new npm bin, new tools, new protocol, new lifecycle daemon), cross-platform from day one. Three high-risk-signal triggers all fire: (1) new exported API surface, (2) new subprocess boundary with its own failure modes, (3) cross-OS behavior in v1.

### Principles (3–5)

- [P1] **Cross-platform is a v1 contract, not a v2 wish.** Every new line of code is written against the §11 compatibility matrix. CI fails the merge on any Windows regression.
- [P2] **The artifact directory enables *post-restart* recovery, not *parent-crash* recovery.** The runner's in-memory state and the parent's in-memory state are both caches. Re-discovery is by reading `events.ndjson`. A clean parent restart rehydrates in-flight workflows from disk; a `kill -9` of the parent kills the runner with it and the in-flight workflows are marked `error: "runner_died"`. (G5 is real; G6 — true parent-crash survival — is a v2 problem per spec §10 Q3, not delivered in v1.)
- [P3] **One runner per Pi session, with a hard concurrency cap (4) on in-flight workflows.** Avoids the spawn cost of one-per-workflow. A single misbehaving workflow can starve the other three (they share the runner's event loop and V8 heap); this is a *known v1 limitation* owned explicitly in the acceptance criteria, and per-workflow spawn is a v2 follow-up.
- [P4] **The existing in-process sub-agent path is untouched.** The runner *imports* `startSubagentJob` from `helpers.ts` (via the new `helpers.shim.mjs` re-export, see T16) but uses its own private `jobRegistry`. Workflows never appear in `get_subagent_status`.
- [P5] **Graceful degradation over hard failure.** If `child_process.spawn` is blocked (sandboxed CI, R9) the runner returns `runner_unavailable` and the rest of the package keeps working. No new feature breaks an existing one.

### Top 3 Decision Drivers

1. **Cross-platform from day one (G9, N5, §11).** The user's hard requirement is that v1 works on macOS, Linux, and Windows. Only a subprocess-based primitive has the cross-process boundary that exposes platform differences — and the only way to ship a v1 that satisfies that requirement is to plan the matrix up front, encode it in lint rules, and gate the CI on it.
2. **Workflows outlive the spawning turn and survive a clean parent restart (G5).** This is the headline property of Plan B over Plan A. The artifact-dir + rehydration design is what makes it work, and it has to be designed in from line 1 — bolting it on later is impossible. (Note: G6, parent-crash survival, is not delivered in v1; see P2.)
3. **No new runtime dependencies (spec §5.2, last paragraph).** The plan must ship with only Node builtins + existing `ndjson` / `is-path-inside`. This rules out `cross-spawn`, `node-cross-spawn-polyfill`, and any platform-specific IPC library in v1.

### Viable Options (≥2 required)

**Option A: Plan B (sidecar subprocess, cross-platform) — RECOMMENDED**
- Pros: Workflows survive the spawning turn (G5) and a clean parent restart (G5, via artifact rehydration), naturally cross-platform once the §11 matrix is honored, full heap isolation between workflow and parent, true preemptive abort via `subprocess.kill()`. (G6 — `kill -9` recovery — is *not* delivered; the v1 runner dies with its parent.)
- Cons: Largest LOC delta (~3,236 LOC new+modified per comparison doc, after T6 re-baselining + T16 shim), new npm bin introduces packaging/install concerns, three new failure modes unique to B (runner-died R1, stdio backpressure R2, protocol drift R3), cross-platform CI matrix adds 1 dev-day of work. Shared-event-loop starvation hazard for concurrent workflows (P3, pre-mortem #4).

**Option B: Plan A (in-process `node:vm`)**
- Pros: Smallest delta (~1,560 LOC), zero new failure modes, 100% reuse of `startSubagentJob` / `jobRegistry`, 3 dev-days.
- Cons: Workflows die with the spawning turn (G5 fails), no parent-crash recovery (G6 fails), one runaway workflow can starve the parent (no heap isolation), **does not satisfy the cross-platform-via-subprocess requirement** (the comparison doc is explicit: "A and C are POSIX/Win-clean by construction but cannot survive parent crashes" and cross-platform via subprocess is the user's stated reason for choosing B).

**Option C: Plan C (`worker_threads`)**
- Pros: Real heap isolation (separate V8 isolate), preemptive abort via `worker.terminate()`, ~1,650 LOC, 4 dev-days.
- Cons: Workflows still tied to parent process lifetime (G5 fails, G6 fails), `postMessage` overhead, single platform-portability story for the `MessagePort` boundary is actually weaker than B's stdio (a Node `worker` on Windows still has its own quirks), no checkpointable resume.

(Plan A and C are listed as the rejected alternatives. Per the user's explicit direction, Plan B is the chosen path. The comparison doc is unambiguous: "For the pi-subagentura project's v2.2.0 release, the choice is Plan B with the cross-platform matrix.")

### Pre-Mortem (3+ failure scenarios)

- **Scenario 1: The runner subprocess silently dies on Windows under load, and the host fails to detect it for >30s.** Symptom: in-flight workflows hang in `running` state, the LLM sees no progress, the user kills Pi, on next start the artifact rehydration surfaces a wave of `runner_died` errors. → **Mitigation:** the `child.on("exit")` handler is the primary detector (R1 mitigation b); the 30s `ping`/`pong` is the secondary detector and is intentionally platform-portable — no `process.kill(0)` (R10, §11 row 8). The `running` count is bounded by the concurrency cap (4), so the blast radius is small.

- **Scenario 2: A workflow script imports `helpers.ts` (via the shim) and the runner fails to resolve the import on the engine floor.** Symptom: `bin/pi-workflow-runner.mjs` exits with `ERR_MODULE_NOT_FOUND` on its first launch, before any workflow runs. → **Mitigation (the v3 fix):** the runner imports `startSubagentJob` from `../helpers.shim.mjs` (a new T16 file, ~20 LOC, hand-maintained, plain-JS, re-exports `startSubagentJob` and `generateJobId` from `helpers.ts`). The shim imports `helpers.ts` via the existing extensionless convention (`from "./helpers"`) which tsc accepts because `tsconfig.json` is `bundler`-resolution. The shim ships in the `package.json` `files` array. **Day-1 spike (T4 acceptance (b)):** `node bin/pi-workflow-runner.mjs --ping < /dev/null` must write a `pong` line to stdout within 1s and exit 0 on EOF, with **no** `ERR_MODULE_NOT_FOUND` on stderr. (Critic refuted the v2 Note claiming Node resolves `.ts` automatically — that is false on Node 18-22.5 and requires `--experimental-strip-types` on Node 22.6+.) The shim is hand-maintained; if `helpers.ts`'s exported signature changes, the shim is updated in the same PR (enforced via code review of any PR that touches `helpers.ts`'s `export { … }` block).

- **Scenario 3: A Windows user hits the 260-char MAX_PATH limit on a deeply nested `~/.pi/agent/sessions/subagentura/workflows/<id>/...` path (§11 row 12).** Symptom: `ENAMETOOLONG` thrown from `appendEvent` / `writeOutput`, the runner reports `error: "io_failure"`, the workflow is lost. → **Mitigation:** the spec commits to a `longPath(p)` helper that prefixes `\\?\` on Windows. This is a Day-1 requirement, not a v2 follow-up — the test "create a workflow whose artifact path exceeds 260 chars" is in the integration test plan (§11 last-but-one row). T13 test 7 is the primary check. **v3 adds a unit test (artifact-walker.test.ts or helpers.test.ts):** "long-path regression — `path.join` and `path.resolve` must not strip the `\\?\` prefix (Node 22.x had a regression; pin the behavior with a unit test)."

- **Scenario 4: A single misbehaving workflow blocks the runner's event loop and starves the other in-flight workflows (runner-starvation hazard).** Symptom: one workflow with a `setInterval(() => {}, 1)` or a synchronous 10-minute `ctx.spawn` blocks the runner's `readline` parser; the other three in-flight workflows stop receiving `progress` events; the parent's NDJSON stream stalls. → **Mitigation (detection):** R1 (30s ping/pong catches a dead runner; `child.on("exit")` catches a crashed one). → **Mitigation (v1 acceptance):** the cap of 4 caps the blast radius but does not prevent starvation of the other 3 — explicitly documented as a known v1 limitation in the T12 acceptance criteria. → **Mitigation (v2):** per-workflow spawn mode behind `--runner-spawn-mode=workflow` CLI flag. The runner's host is structured to make this v2 change a one-flag switch, not a re-architecture.

- **Scenario 5 (cross-platform install hazard):** `npm install` of a fresh checkout on a Windows machine fails with `EACCES` because npm tries to create the `.cmd` shim for `pi-workflow-runner.mjs` and the parent's `node_modules/.bin/` is on a path that has an existing ACL denying script execution. Symptom: install fails, the user gets a generic npm error. R13 covers discovery, not install. → **Mitigation:** the T14 acceptance criterion includes "`npm install` on `windows-latest` (CI smoke) completes without errors." The `.cmd` and `.ps1` shims must not be checked into the repo (npm creates them); the bin field in `package.json` must point at a file that exists at install time. The T13 pack-check smoke also installs the packed tarball in a temp prefix, exercising the install path on all three OSes.

- **Scenario 6 (artifact-write-then-parent-dies hazard):** The parent pi process exits via `SIGTERM` (e.g., a CI runner that timed out) while the runner is mid-write to the artifact dir. Symptom: the workflow's `output.md` is written, the `events.ndjson` is complete, but the runner also receives SIGHUP via the process group and exits before sending a `done` NDJSON message. The next parent start does not pick up the result because the runner is also dead and no `done` was ever delivered. → **Mitigation:** on parent restart, `host.rehydrateFromArtifacts()` detects the *terminal* state (a `done`/`error`/`cancelled` event in `events.ndjson` with no in-flight child) and surfaces it via `get_workflow_status`/`get_workflow_result`. The T13 integration test list (item 12, added in v2) covers "Parent restarts after runner-died-with-output-written; result is rehydrated from artifact dir."

- **Scenario 7 (sub-agent model-consistency hazard):** A workflow calls `ctx.spawn`, which calls `startSubagentJob` (via the shim), which imports `@earendil-works/pi-coding-agent`'s `createAgentSession` — and the Pi runtime initializes an `AuthStorage` and `ModelRegistry` *inside the runner process*. Symptom: workflow sub-agents behave inconsistently with parent sub-agents because the runner has a different `cwd` and a different `process.env` from the parent. → **Mitigation (v1):** documented as a known quirk in the protocol doc (Q10 in Open Questions); workflow sub-agents always use the runner's own model discovery. The T12 host unit tests assert that the runner's `startSubagentJob` call uses the runner's `ModelRegistry`, not the parent's. → **Mitigation (v2):** the parent passes `defaultModel` and `parentModelRegistry` in the `start` message (Q10, recommended for v2).

- **Scenario 8 (NEW — `helpers.shim.mjs` Day-1 spike):** The shim is a 20-LOC file that re-exports `startSubagentJob` (and any other symbol the runner needs, e.g. `generateJobId`). If the implementer forgets to add a symbol to the shim when `helpers.ts` exports it, the runner fails at runtime with a `TypeError: undefined is not a function` deep inside a workflow. → **Mitigation:** the shim is *intentionally* minimal — only the symbols the runner actually imports are re-exported. The Day-1 spike (T4 acceptance (b), see also T16 acceptance) imports `startSubagentJob` from the shim and `import type { … } from "./helpers.ts"` for types (erased at runtime). The shim is code-reviewed on every PR that touches `helpers.ts`'s export list. A v2 enhancement could add a `tsc` script that *generates* the shim from `helpers.ts`; v1 ships it hand-maintained.

- **Scenario 9 (NEW — cold-start latency):** The first `run_workflow` call in a Pi session has cold-start latency: spawn (50-200 ms) + ESM imports (100-300 ms) + `WorkflowRegistry` init (10-50 ms) = 200-600 ms total. Subsequent calls (with the runner already running) are ~10-50 ms. If the LLM's tool call is the first one in a session, the user-perceived latency is the cold-start cost. → **Mitigation:** (a) lazy-import heavy modules in the runner — `import("./helpers.ts")` (or the shim) is *not* top-level; it's deferred to first `ctx.spawn` (matches the v1 design — workflows that never call `ctx.spawn` skip the heavy import entirely). (b) The README's "Workflows" section documents the cold-start cost ("the first call in a session spawns a new runner and may take 200-600 ms; subsequent calls are sub-50 ms"). (c) v2: warm-pool the runner at `session_start`.

## Architecture Decision Record (ADR)

**Decision:** Ship Plan B (sidecar subprocess runner, cross-platform from v1) as the workflow primitive in pi-subagentura 2.2.0, with a hand-maintained `helpers.shim.mjs` re-export module (T16) to bridge the runner's runtime resolution to `helpers.ts`.

**Drivers:** Cross-platform from day one (G9/N5/§11) — only a subprocess boundary gives the cross-process isolation the user requires. Workflows outlive the spawning turn and survive a clean parent restart (G5) — the artifact-dir design is the only path to that property. (G6 is a v2 problem; see P2 and Open Questions Q3.) No new runtime deps — every Plan-B primitive is in the Node stdlib or already on the dep list. **The shim decision:** the runner cannot `import "../helpers.js"` because the package only ships `helpers.ts` and Node's default ESM resolver does not auto-fallback to `.ts` extensions (Critic test, Node 26.2.0 → `ERR_MODULE_NOT_FOUND`). Of the three options, the shim is the smallest, most portable, and does not require an `engines.node` bump or a build step.

**Alternatives Considered:** Plan A (in-process `vm`) — rejected because it does not deliver G5/G6. Plan C (`worker_threads`) — rejected for the same reason. **R12 fix options (v3):** (A) plain-JS shim — **CHOSEN**; (B) bump `engines.node >= 22.6.0` + `--experimental-strip-types` — rejected (engine bump is a breaking change for the wider Pi ecosystem on Node 18/20); (C) build step (`helpers.ts` → `helpers.js`) — rejected (contradicts `tsconfig.json: noEmit` philosophy and adds a `prepublishOnly` step that the package has never had).

**Why Chosen:** The user's hard requirement (cross-platform + resume) maps 1:1 to Plan B's two unique properties. The shim is a 20-LOC, hand-maintained file that re-exports the ~2-3 symbols the runner actually needs. The shim's only cost is "remember to update it when `helpers.ts`'s public exports change," which is enforced by code review of any PR that touches `helpers.ts`'s export list. The cost (~3,236 LOC total, 8 dev-days including the cross-platform matrix and the shim) is the minimum cost of those properties.

**Consequences:** *Positive:* workflows keep running while the user types a new prompt, clean parent restarts rehydrate in-flight workflows from the artifact dir, the v1 is genuinely cross-platform via the §11 matrix, the runner can be re-purposed in v2 as a true daemon without re-architecting. The shim is a small, well-isolated file that an implementer can reason about in 5 minutes. *Negative:* the new bin adds ~25 KB to the published tarball (mild), a sandboxed CI that blocks `child_process.spawn` will see `runner_unavailable` (degrades gracefully, P5), three new failure modes (R1/R2/R3) ship in v1, a single misbehaving workflow can starve the other three in-flight workflows (shared event loop; pre-mortem #4), a malicious or careless workflow can persist secrets to `events.ndjson` (R15; user-trust), the shim must be hand-maintained.

**Follow-ups:** v2 named-pipe / Unix-socket transport (Q2) replacing stdio; v2 platform-appropriate detach (Q3) for full POSIX daemonization; v2 `restart_workflow` tool for resuming from artifact dir; v2 per-workflow spawn mode; v2 `defaultModel`/`parentModelRegistry` fields in the `start` message; v2 `--trust=untrusted` mode for sandboxed workflows; v2 tsc-generated shim (replaces the hand-maintained `helpers.shim.mjs`); v2 warm-pool the runner at `session_start` (pre-mortem #9 mitigation (c)).

## Task Breakdown

Each task lists: file paths (existing files to modify, new files to create), key exports, dependencies, and an estimated LOC delta. Acceptance criteria are listed in the next section.

**Task 1: NDJSON protocol types and validator** — *new* `workflow-runner-protocol.ts` — ~200 LOC — deps: none — key exports: `ParentToRunner` type, `RunnerToParent` type, `validateMessage(raw: string): ParentToRunner | RunnerToParent | null`. Foundation for every other task that talks to the runner.

**Task 2: Workflow allowlist module** — *new* `workflow-allowlist.ts` — ~80 LOC — deps: none — key exports: `isAllowedWorkflowPath(p: string): boolean`, `WORKFLOW_PATH_ROOTS`. Imported by both the parent (tool-time validation) and the runner (defense in depth).

**Task 3: Workflow combinators and sandbox** — *new* `workflow.ts` — ~250 LOC — deps: T1, T2 — key exports: `WorkflowContext` interface, `parallel()`, `series()`, `define()`, `buildSandbox(ctx)`, `WORKFLOW_PROTOCOL_BANNER`. The combinators and the sandbox builder live in the parent process; the executor lives in the runner (Task 4).

**Task 4: Runner binary** — *new* `bin/pi-workflow-runner.mjs` — ~700 LOC — deps: T1, T2, T3, **T16 (the shim)** — *standalone ESM `.mjs` (no build step, the repo's `tsconfig.json` is `noEmit`)*. Internal: shebang+argv, `StdioTransport`, `WorkflowRegistry`, `WorkflowExecutor`, NDJSON handlers, `CLI_SOURCE` mirror of `subagent-artifact-cli.ts:28-69`, stderr-only logging honoring `SUBAGENT_DEBUG_LOG_DIR` (per `helpers.ts:32-49`). **Import statement (T6 MAJOR-4, v3 explicit):**
  ```js
  // bin/pi-workflow-runner.mjs (top-of-file imports)
  import { startSubagentJob, generateJobId } from "../helpers.shim.mjs";
  ```
  The shim (T16) re-exports the runtime symbols; types are imported via `import type` directly from `../helpers.ts` and erased at runtime. The shim is hand-maintained and must list every symbol the runner needs (see T16 for the exact list).

**Task 5: Workflow runner host (in-parent)** — *new* `workflow-runner-host.ts` — ~400 LOC — deps: T1, T3 — key exports: `class WorkflowRunnerHost { constructor(opts), ensureRunning(), startWorkflow(req), cancelWorkflow(id), shutdown(), getActivityRows(), rehydrateFromArtifacts() }`. Subprocess management (no `shell: true`, `windowsHide: true`, `stdio: ["pipe", "pipe", "pipe"]`), message routing, artifact writes via `appendEvent`/`writeOutput` (`artifact.ts:67`, `:77`), TUI integration (see TUI widget coexistence paragraph below), rehydration on `session_start` mirroring `subagent.ts:972-974`. **TUI widget coexistence (v3 MAJOR-2, made explicit):** The TUI uses **two separate widget keys**, registered with independent `ui.setWidget(key, rows, opts)` calls. `subagentura-activity` is registered at `subagent.ts:590-594` for the existing in-process sub-agent rows. `subagentura-workflow-activity` is registered by the host at the same `placement: "belowEditor"` for workflow rows. **They are independent — both can be active simultaneously, each with its own row list, each with its own visibility predicate.** The runner workflow widget rows show: workflow count, name (derived from `script` filename), `phase` from the most recent `progress` message, time-since-last-event. The T13 test 11 assertion is that *both* widget keys are set (`ui.setWidget` called twice) when the runner is running, and the existing `subagentura-activity` widget is *not* overwritten by the new workflow widget.

**Task 6: Tool registration in `subagent.ts`** — *modify* `subagent.ts` — **+300 LOC delta (re-baselined from +180; see Acceptance Criteria)** — deps: T4, T5, T7 — **import statement (T6 MAJOR-4, v3 explicit):**

### Lint scope (R10 mitigation b, in detail)

The R10 lint rule is **scoped to the new files only** so it does not fail on the existing `subagent-artifact-cli.ts:75,77` (which uses `chmodSync(targetPath, 0o700)` in `writeCliScript`). The repository's ESLint config (either `eslint.config.js` flat config or `.eslintrc.json`, whichever is in use — to be confirmed in the Day-1 R10 spike) gets the following `overrides` block:

```js
// eslint.config.js (flat config) — illustrative, not the final shape
{
  files: [
    "bin/pi-workflow-runner.mjs",
    "workflow.ts",
    "workflow-allowlist.ts",
    "workflow-runner-protocol.ts",
    "workflow-runner-host.ts",
    "artifact-walker.ts",
    "helpers.shim.mjs",          // T16, NEW
    "demos/audit-xss.mjs",
  ],
  rules: {
    "unicorn/prefer-path-platform": "error",
    "no-restricted-syntax": [
      "error",
      { selector: "CallExpression[callee.object.name='chmodSync']", message: "Use fs.promises.chmod and gate on process.platform === 'posix' (see §11 row 5)." },
      { selector: "CallExpression[callee.object.name='chownSync']", message: "POSIX-only; see §11 row 5." },
      { selector: "Literal[value=/~/]", message: "~ paths are POSIX-only; use path.join(os.homedir(), ...) (see §11 row 2)." },
    ],
  },
}
```

For the legacy `.eslintrc.json` shape, the equivalent is `overrides: [{ "files": [...], "rules": {...} }]`. The existing `subagent-artifact-cli.ts` is **explicitly exempt** because it predates the rule and its `chmodSync` is the established pattern. Future PRs that introduce new `chmod` calls in *unlisted* files will not be caught by this rule; the §11 row 5 cross-platform test in T13 is the secondary defense.
